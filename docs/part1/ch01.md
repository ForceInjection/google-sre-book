## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 站点可靠性工程 | Site Reliability Engineering (SRE) | 既指专业领域，也指从业者个人与团队；上下文决定含义 |
| 服务可靠性层级模型 | Service Reliability Hierarchy | Dickerson 2013 年提出，灵感源于 Maslow 需求层次：自底向上为监控→应急响应→复盘→测试发布→容量规划→开发→产品 |
| 现代生产健康层级模型 | Production Health Hierarchy | 第2版提出：社会技术基石→态势感知→常态化备战→基础设施设计→韧性产品→涌现式可靠性 |
| 琐事 | Toil | 手动、重复、可自动化、战术性、缺乏持久价值的运维工作；Google 内部以 50% 为上限 |
| 涌现式可靠性 | Emergent Reliability / Reliable by Default | 可靠性自然融入基础设施、流程与文化，成为"默认可靠"的生态体系 |

## 关键论点

1. **可靠性是第一位的功能特性**。功能再丰富，宕机或卡顿就毫无价值——如同配置豪华但不能开动的轿车。
2. **SRE 必须是专职角色**。兼职做 SRE 很难成功：没有专属时间投入、没有专家社区支撑，随时会被挤出优先级基线。
3. **SRE 是协作型赋能者，不是守门人**。运维维系可靠的生产环境能显著提升研发生产力，形成"健康研发实践孕育健康生产系统"的良性循环。
4. **软件工程思维带来三大优势**：本质层理解（可复制、可迁移的经验）、自动化（效率 + 一致性，并倒逼流程精简）、开发运维同一语言（从生产逆流而上的反馈闭环）。
5. **每个 SRE 都应具备编码能力**——哪怕只是配置一条监控规则；理想状态是兼具软件工程与系统工程素养。
6. **无需彻底建完某一层才能迈向下一层**：底层达到一定成熟度即可让上层推进变得容易；应横向纵向同时推进，但避免在根基不稳时盲目堆上层（倒金字塔只会徒耗精力）。
7. **文化转变要从小处着手**：聚焦具体行动与行为模式（日积月累的行为终将重塑文化），比空谈文化变革切实得多。

## 各层级要点（全书的路线图）

| 层级 | 核心内容 | 深入章节 |
|---|---|---|
| 社会技术基石 | 心理安全感、无指责与信任、持续改进、自主权与激励 | 第4~7章 |
| 态势感知 | 可观测性、SLO（把"用户满意度"量化）、告警与仪表盘、琐事追踪 | 第8、9章 |
| 常态化备战 | 事故管理、事后总结、培训与文档；前瞻性风险管理（STPA/CAST） | 第5、10~12章 |
| 基础设施设计 | 发布管理（CI/CD、增量发布、主干开发）、配置管理（GitOps、特性开关）、数据管理、容量管理、生产测试（prober/混沌工程）、可观测性平台 | 第13~16章 |
| 韧性产品 | 缩小爆炸半径（故障域拆分、故障自动转移）、优雅降级、服务简化 | 第17、18章 |
| 涌现式可靠性 | 平台杜绝整类故障、赋能开发人员、组织级协同 | 第19~23章 |

## 实践要点

- [ ] 用三个判据检验日常工作：契合业务目标？提升可靠性？工程化方法？
- [ ] 追踪琐事占比，超过 50% 即为红线（是上限，不是目标）
- [ ] 发布管理优先做：CI/CD + 增量式发布 + 主干开发 + 特性开关
- [ ] 配置数据纳入版本控制与代码评审（GitOps 思想）
- [ ] 用探测器（prober）与故障注入测试主动暴露问题
- [ ] 设计阶段就缩小故障爆炸半径：故障域拆分 + 优雅降级（如头像服务故障时页面主体仍可加载）
- [ ] 赋能开发者：教育与自助平台比"由 SRE 全盘推动"力量大得多
