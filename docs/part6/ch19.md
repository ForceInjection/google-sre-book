# 第19章 · 处在转折点上的 SRE

> [!INFO] 出处

**一句话概括**：当生成"勉强可用代码行"的成本趋近于零，SDLC 的阶段边界被急剧压缩；本章逐项推演生产运维工作在 AI 开发时代的走向——变更速率、技术债、版本控制、预发布环境、调试、事故、技能与可观测性——并给出底线判断：在 AGI 到来之前，人类仍是"兜底的最终理解者"。

## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 软件开发生命周期 | Software Development Life Cycle (SDLC) | 计划 → 分析 → 设计 → 构建 → 测试 → 部署 → 维护的阶段模型；概念可追溯约 60 年（1968 年 NATO 会议首提"软件危机"，Royce 1970 瀑布模型） |
| AI 开发 | AI dev | AI 驱动的软件开发（命令行工具、编辑器插件、流式内嵌等）；注意区别于"AI SRE"（AI 辅助乃至自主执行的生产工程活动） |
| 非功能性需求 | Non-functional Requirements | 性能、质量、可靠性、安全性、可测试性等；改一行代码即可破坏，无法只在某一阶段保障，必须贯穿全周期 |
| 串行化与循环 | Serialization & Loops | SDLC 两个核心理念：阶段先后分离关注点；同时可回退到前序阶段重做（维护阶段尤甚）——两者存在张力 |
| 康威定律 | Conway's Law | 人际沟通结构决定软件架构结构；AI 开发打破它：单人加单个智能体即可把需求一路推进到生产 |
| 战略性不协调 | Strategic Incoherence | AI 开发产物的典型特征：能完成复杂的低上下文任务，但功能集一扩再扩后整体连贯性与协调性逐步退化 |
| 向前修复 | Roll Forward | 变更速率过快使"挑拣提交"（cherry-picking）与回滚（rollback）失效后，靠持续前推收敛到正确行为 |
| 规范驱动开发 | Specification-driven Development | 把通用设计原则与架构文档化，克制纯局部优化与增量交付的弊端，让人类与 AI 保持步调一致 |
| 样本分布外 | Out-of-sample | 基于 Token 预测的 AI 在超出训练分布情形下表现不理想——这正是"未知的未知"事故持续存在的技术根源 |
| 兜底的最终理解者 | Understanders-of-last-resort | 本书的结论性定位：人类对系统的理解从"创造之时"退守为"故障发生之时"，但仍是最后的理解手段 |
| 技能退化 | Skill Atrophy | 久疏战阵的排障技能会生疏脱节；工具只在部分时间给出正确建议时，风险反而被放大 |

## 关键论点

1. **真正变贵的是别的东西**。生成代码行的成本趋零后，昂贵的是可靠性与安全等非功能性需求：它们无法压缩进某一阶段，必须贯穿全周期；而已有证据表明 AI 生成的代码可靠性甚至更低——缺陷流入生产的历史规律并未改变，不调整工作方式，可靠性就不会提升。
2. **AI dev 夺走了"渐进打磨的从容"**。各阶段需求未变但耗时骤减，产出暴增；过去长达两周的构建期允许边构建边微调，如今两小时的构建不再有这种余地。验证速度变快主要惠及功能性需求，而非功能性需求。
3. **康威定律被打破，SDLC 的社会化属性迎来重估**。流量优先于免费还是付费这类权衡本无客观正解，靠会议室共识；AI 可以推荐策略、全权接管乃至重新设计系统消除权衡本身——由社会化共识塑造的惯例与经验法则将面临前所未有的严格审视。
4. **部署这道墙没有变**。测试驱动开发让位于"近乎不间断持续运行全系统测试 + 自动化评测"，构建与测试已然融合；但部署的硬性边界与失败后果依旧：生产环境的世界根本不在乎你是否用了 AI。
5. **变更速率是分母**。其余不变而交付提速 10 倍，事故、脆弱交互、资源耗尽大概率同步 10 倍，且很难期望它是亚线性的；应对之道是把 AI 也用于事前预防：挖掘系统拓扑、源代码与事后总结提炼通用方案（可与 STPA 结合），并以测试框架、评测框架与 LLM 交叉评审放大"稳定化效应"。
6. **战略性不协调是新型技术债制造机**。同一段实现以略微不同的形式在代码库中反复重写（违反 DRY），从类级别蔓延到子系统级别；重复代码推高复杂度直至撑爆上下文窗口，AI 随即无法胜任——技术债最终要在生产环境偿还高昂利息。
7. **版本控制从"选版本"转向"控边界"**。API、二进制、协议的"特定版本"在线上可能已经变化，甚至要按请求、按会话、按用户划分版本；正如当年从"单机非正常即宕机"跃迁到"机器群常态部分宕机"，我们不追求全员同版本，但必须掌控版本转换发生时的边界条件与环境。
8. **生产调试从读代码转向动态构建上下文**。部署软件数量指数级增长后，无人能靠阅读代码库建立排障上下文；工具实时推断"发生了什么"与"预期是什么"，人工介入终将力不从心，甚至催生"自动恢复失败即自动销毁重建"的隔离式架构。
9. **事故仍属于人类**。软件故障本质不可预测，token 预测模型对样本分布外情形乏力，LLM 幻觉概率不可忽略，面向公众的重大故障中断无论自动化多强都需要人工问责与可解释性；因果链更长更绕，排查耗时可能不降反升。
10. **警惕两股反向力量**：一是技能退化——SRE 处理的恰是概率分布长尾端的罕见极端事件，而为常见情形设计的工具在此最不可靠；二是"响应太便宜"——应急工具越高效，事前预防分到的资源越可能被削减，系统性预防被轻视。
11. **SRE 的价值需要重新诠释，而非会缩水**。运维生产系统的重要性与难度没有降低，只是必须配备更多工具才做得动；部署前的工作可能更重要，角色更接近"资深工程师"（staff engineer）：全局视角加微观洞察，依然深谙软件之道。

## 生产运维环节速查表

| 环节 | 预期变化 | 应对思路 |
|---|---|---|
| 变更速率 | 突破人类反应极限；回滚让位于向前修复 | AI 事前预防 + 稳定化效应（测试/评测/交叉评审） |
| 技术债 | 战略性不协调、代码反复重写 | 规范驱动开发，架构与原则文档化 |
| 版本控制 | 隔离风险手段失效 | 掌控版本转换的边界条件与环境 |
| 预发布环境 | 难以模拟生产行为，维护成本或不可行 | 接受模拟失真，强化生产内验证 |
| 生产调试 | 依赖工具动态构建上下文 | 即时推断预期行为，向前修复收敛 |
| 事故 | 未知的未知持续存在，排查耗时拉长 | 人类问责与可解释性不可或缺 |
| 技能退化 | 排障手艺生疏、长尾事件更棘手 | 坚持厄运之轮类演练 |
| 可观测性 | 门槛降低但指标泛滥、重复 | AI SRE 成为事实上的可观测性核心层 |
| 形式化方法 | 描述系统行为更可行高效 | 确定性保证 + 全面测试补充 |

## 实践要点

- [ ] 把每次发布当作"世界模型破裂"的潜在契机：向生产推送任何变更都意义重大
- [ ] 为 AI 生成的代码补自动化评测：人类已无力监督持续运行的全系统测试
- [ ] 用规范驱动开发把设计原则与架构文档化，让人类与 AI 步调一致
- [ ] 在人工评审之上叠加测试框架、评测框架与 LLM 交叉评审，管控风险
- [ ] 挖掘系统拓扑、源代码与事后总结，让 AI 提炼可全系统复用的预防方案，并守住事前预防的资源投入
- [ ] 为版本混沌做准备：回答"线上实际运行的是什么"，并掌控版本转换边界
- [ ] 保留厄运之轮等排障演练，对抗技能退化——工具越强越要练
- [ ] 关注"为什么这么改"的上下文留存：缺失它，故障调试的搜索空间急剧膨胀
- [ ] 试点形式化方法：对关键行为给出确定性保证，再以测试兜底
- [ ] 厘清团队对 AI 建议的授权边界：按下执行按钮省心，但长尾事件可能灾难性翻车
