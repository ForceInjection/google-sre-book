# 第17章 · 面向韧性的系统设计

> [!INFO] 出处

**一句话概括**：韧性是"系统在超出原始设计预期的异常状况下仍能保持服务质量并恢复"的能力——本章给出一套贯穿风险、变更、依赖、故障域、过载、输入、数据与紧急模式的原则性方法论，并强调用技术手段而非制度条文把韧性强制落地。

## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 韧性 | Resilience | 系统通过自动化机制或受训人员/AI Agent，检测并诊断修正活跃故障模式的能力，即使是设计之初未预料的新型故障 |
| 负载卸载 | Load Shedding | 在请求到达之初直接拒绝，避免半途失败白白浪费计算资源 |
| 优雅降级 | Graceful Degradation | 返回降级响应（过期缓存、精简结果），以低计算开销交付一定价值 |
| 故障域 | Failure Domain | 相互独立的部署/隔离单元（区域、可用区、逻辑分区、运维分片），单域故障不扩散 |
| 自适应节流 | Adaptive Throttling | 客户端按近期成功率动态调整请求速率，高失败率时主动减流 |
| 特性开关 | Feature Flag | 潜在高影响改动保持默认禁用，出事时改一个配置即可回滚 |
| 紧急刹车 | Emergency Stop | 以预期且内在安全的方式中止正在进行的变更活动 |
| 合格性验证 | Qualification | 在真实受控环境中持续验证系统与团队的韧性特性 |
| 紧急模式 | Emergency Mode | 故障阻碍常规响应工具时的运维模式（正常→紧急→灾难三级） |
| 关键用户旅程 | Critical User Journey (CUJ) | 用户最在意的功能路径；依赖分级与响应 CUJ 均以它为准绳 |
| 响应 CUJ | Response CUJ | 应急响应所需的最小能力集：comms/imag/dash/reach/doc/priv/dbg/fix 八类 |

## 关键论点

1. **韧性与可靠性不同**：可靠性是在既定设计范围内持续达标；韧性是靠预案在更恶劣环境下保持高水准，甚至应对始料未及的故障——它为用户带来业务连续性保障。
2. **韧性的三种落地途径**：以合理成本效益处置所有高概率故障；优先处置高影响故障；妥善应对破坏力最大的低概率故障。多数组织把五个九（99.999%）作为务实上限，但一些"训练有素的忽略"（~0.001%）一旦爆发可能烧光数十年错误预算，至少应评估低成本缓解手段。
3. **Google 的可靠性/韧性原则**：涵盖风险管理、变更管理、依赖管理、故障域、过载管理、输入验证、数据韧性、能力合格认证、应急模式九个方面；依托标准化生产平台，许多原则默认即符合，并借此逐步淘汰私有解决方案。
4. **原则必须靠技术强制落地**：制度文本终有过时之日，认知负荷与日俱增；用指标度量、平台级默认配置与代码化程序强制执行，才能获得持久性（度量有效性作为投入反馈）与复利效应（实践固化为代码后，替换成本低、干扰小）。
5. **统一性必须绝对奏效**：韧性方案应尽量简单，且绝不能失效；统一降低认知负担，但须识别何时值得为特定应用定制化。绿地系统先启用全部方案，棕地系统谨慎改造、优先集中最关键者，让"缺乏韧性方案的存量系统数量不再膨胀"。
6. **风险管理是纵横向结合**：团队提供纵向（垂直）视角——响应式与前瞻式数据（故障促因、变更速率、告警效率、组件关键度）；管理层汇总为横向视角，制定全局指导原则并防"旁观者效应"。STPA/CAST（见第12章）是结构化识别手段，但它们不是数据。
7. **按成本视角排序风险**：高/中概率故障优先做执行维护成本低且默认开启的方案（断路器、节流、发布阻断）；低影响低概率明确接受并登记风险登记册（risk register）；高影响低概率则先写预案再按优先级投入——排序原则：自己遭遇过的 > 他系统遭遇过的 > 行业公认可能的 > 已知未知（known unknowns）。
8. **变更管理核心是"粒度权衡"**：变更范围越大受影响面越广；小粒度变更必不可少，但过小拖慢节奏、过大难以推演。所有变更渐进式发布、多变更勿并发（二进制与数据更新独立推进，先单可用区再扩展）；Google 的金丝雀分析服务（CASI）自动监控各副本健康度，达标才标记为正式对外服务。
9. **通用安全缓解手段**：流量切除（drain）、回滚（rollback）、扩容（upsize）、服务降级（degrade）、阻断拦截（block，防"死亡之查询"）。回滚往往是最安全的首选；缓解手段自身也必须遵循变更管理原则并定期演练。Google 还定义了常规→中等→高→极高四级变更敏感度，在敏感期暂停非必要生产变更。
10. **纵深防御**：问题暴露得越早越好——特性开关把回滚简化为改配置，紧急刹车提供中止变更的心理安全感与实质安全网；由相互独立的系统从客户端信号监控变更健康度。
11. **依赖管理 = 表征 + 控制**：准确表征全部生产资产并附元数据，机制上严格限制可引入的依赖（对照 ACL 检查库与 RPC 端点）、对违规告警。依赖分为可选（具备容错能力，应故障开启 fail-open）与必需（故障即破坏核心功能，需兜底或 fail-closed）。
12. **保护下游依赖方**：你的系统也是别人的依赖项——事故响应人员需要快速识别受影响的下游及其 CUJ；变更发起者可在重要度最低的节点先行变更；降级模式时可将健康依赖项变更敏感度调至"最高"以保护剩余功能。
13. **兜底方案（fallback）管理**：维护早期版本部署于独立故障域，或构建低依赖的精简独立实现——前者成本低但共享底层组件的"命运"，后者昂贵但几乎不与主系统共命运。高价值系统理应配备更健壮的兜底。
14. **故障域必须真实隔离**：划分依据是故障本质——客户端行为、应用程序组件、上游基础设施、物理基础设施；隔离类型有逻辑地理、逻辑功能、基础设施、运维四类（Google 值班两分片、每分片主副两值班员，即运维隔离的实例）。错误的隔离只是虚假安全感。
15. **对齐故障域**：2 区域 × 各 2 可用区、节点均匀分布时，单可用区瘫痪最多损失 25% 全局容量；若每区域仅一个可用区，风险升至 50%。避免组件分散得过开的反模式，扩展时增加可用区而非扩大现有规模，以防"雷群效应"（thundering herd）。
16. **故障域恢复四步**：隔离（Isolate）→ 就地修复（Repair）→ 重新组装（Reassemble）→ 触达（Reach）远端故障域并逐个拉回；远端恢复须含衡机制，全局性恢复能力应仅在通过安全评估的指定位置运行。
17. **防止全局状态损失**：所有全局性组件与功能都应在至少一个故障域内保留"原始、已知良好"状态（数据、配置与二进制）；可设少量"原始"分区，发布落后数个版本、严禁紧急发布、仅允许监控流量接入——它们不是热备，而是封存的全局状态副本。
18. **过载下保持有效吞吐**：接收流量的系统故障表现不应与过载程度不成比例——配置 X 容量的系统面对 10X 冲击应继续提供接近 X 的服务，过载退去后无人介入自动恢复。三种策略：服务端按优先级削减低优流量（甚至 100% 错误）、提供降级响应（如耗 20% 计算量达 80% 质量）、客户端主动减流。
19. **级联故障的典型表现**：请求队列严重积压、RPC 超截止时间引发重复请求、容器频繁重启、缓存失效后雪崩式预热负载；必须把流量压低到系统可承受水平，同时为受损容量争取恢复窗口。
20. **客户端控制三原则**：指数退避（exponential backoff）＋随机抖动避免负载尖峰；重试严格限制在单层客户端内部，防止"客户端的客户端"连锁重试；自适应节流按错误概率历史记录自我调节，并结合请求重要级别信息。
21. **隔离过载**：按用户维度实施配额（quota），超限即快速响应；单请求级与单服务级的重试预算在连续失败后向用户传递故障，防止跨故障域连锁重试。
22. **切实可行的应急缓解**：封禁过量请求来源（阻断"致命查询"）、调配补充资源、阻止服务器重启（假死组件重启只会进一步削减容量）、对确认无有效吞吐（goodput）的服务器加快重启，并为冷启动制定周密预案以防客户端急切刷新引发雷群。
23. **输入验证遵循鲁棒性原则**："发送时要保守，接收时要宽容"，但对异常输入要能安全失败（fail safe）。异常类型包括：空更新（ACL 变空白即全锁死）、部分更新（流式 RPC 截断）、损坏更新（比特位翻转）、新型错误数据（只定义"有害数据"黑名单必漏边界）、过期既有数据。
24. **可落地的系统加固**：识别异常过大的 diff 并附加校验（配额列大幅缩减须额外确认信号）；部分更新携带预期大小等冗余校验字段；规范输入格式（稳定排序、禁止重复项）；在内存中保留一切早数据以便瞬时回滚（无需从持久层重新检索）。加固后的系统收到异常输入还应触发告警，收集趋势数据反哺风险管理。
25. **数据韧性高于单层冗余**：元数据丢失后的恢复、加密密钥（DEK/KEK）的恢复、例行运维误下线关键副本、写一次（write-once）存储拦截机制失效——都是概率低但影响全局的理论场景，应对速度生死攸关。
26. **数据操作去全局化**：存储配置与二进制发布严格限制范围；节点状态变更在全局冗余不足时暂停；已存数据的变更（如立即删除 Blob）须范围受限且理想情况下可逆；高危操作须可观测、对自动化脚本同样去全局化、对特权提升加固防御。
27. **正确执行删除与恢复**：只允许分阶段删除并内建不可跳过的宽限期（"移到回收站"）；被删关键数据保留至少 X 周；用最小外部依赖实现恢复（软删除"撤销删除"、防删除备份、重写回在线库）。删除安全规范应组织级落地并纳入审计，容留时间更长的数据存储成本只摊给最有价值的业务场景。
28. **关键数据的独立降级回退**：关键数据（元数据、加密密钥）与恢复流程绝不能共享依赖（shared fate）；可将 PostgreSQL 元数据备份到独立 PostgreSQL 实例，或备份到架构截然不同的另一套数据库系统——两者兼得最理想；降级备份自身须具备防护（只读备份须确保任何读写都无法损毁已备数据）。
29. **合格性验证四维度**：时效性（测试用例随事故教训及时更新）、真实性（覆盖正常/应急/灾难模式，预生产与生产环境合理搭配）、理论演练（沙盘推演，如第Ⅰ版第28章的"灾难角色扮演"，在剔除高危操作的前提下走通全部交互）、全员参与（自动化、常态化、周期化，权责划分清晰）。
30. **测试左移与逼真环境**：早期验收便宜但保真度不足，后期环境真实但排错昂贵；对无需完整生产复杂度的预期韧性行为仅用准生产环境测试，以建立安全记录。高保真环境（如演练丢失表行后的在线恢复、带宽隔离下的路由器回滚）可多用途复用以摊薄成本。Google 的韧性工程团队维护模拟灾难条件的逼真环境，为 DiRT 测试搭台，曾借此发现局部循环依赖与"彻底瘫痪但极易修复"的异常行为。
31. **紧急模式的分级**：正常模式（强依赖系统、标准接口）→ 紧急模式（低依赖回退系统，可能需轻微适应，多数响应人员经极少培训即可上手）→ 灾难模式（零依赖组件、协同调用接口，须严格技能培训的精专运维团队）。本章聚焦紧急模式，因其发生概率远高于灾难事件。
32. **开发人员的紧急模式装备**：坚持低依赖设计（核心系统可自举 bootstrap）、保持接口一致性（切换回退系统时仅改访问地址）、明确定义回退能力、支持模式平滑切换（显式状态指示）、故障期间保持基本可用性（GUI/CLI 优雅降级）、坚守安全基线（任何模式下安全态势绝不能降级，防止绕过安全防御的行径）。
33. **响应人员按结构化决策树行动**：常规工作流可用？→ 保持正常模式专注缓解；系统是否提供应急备用方案指导？→ 有则切换紧急模式，无则等待修复或由在岗专家组建响应团切换灾难模式；积极拥抱备用方案、优先提供指导而非盲目自动化、预留混合模式（如缓解 Google Chat 故障时仅启用备用沟通工具）。
34. **管理层职责**：宏观缓解措施、修复应急工作流的功能退化（警惕备用方案与主系统产生循环依赖的退化）、制定并推进响应 CUJ、用制度纪律抵消人性忽视低概率风险的倾向。
35. **响应 CUJ 八大类**：comms（建立沟通渠道）、imag（IMAG 协议协调应急响应）、dash（知会利益相关方）、reach（访问系统）、doc（查阅文档）、priv（激活权限）、dbg（排查系统）、fix（修改系统）。每个 CUJ 须具备组合性与冗余性，并映射到正常系统与备用系统（如 comms-text：正常用 Google Chat，应急用 IRC/蜂窝电话直拨）。
36. **培训与演练的区别**：培训让你理解有哪些 CUJ 及其原理；演练让你在真正需要前积累实战经验。演练优先级：先练修复生产环境的核心前置动作（reach/comms/priv/doc/imag），再练通用动作（dash/dbg/fix），最后才是系统定制的专属动作。
37. **展望与付诸实践**：韧性改进的收益难以直观证明（"证明否定命题"），先解决能估算损失成本的高频故障，再为绝不可承受的低概率极端场景制定"切实带来改变"的应对计划；用评估准则（rubric：故障影响全局/局部？fail-open 还是 fail-closed？）给预期行为排序，从"最没有理由不具备防范"的领域入手，绿地与棕地分开评估，堆栈排序（stack-rank）后对 ROI 较低的类别也要抽检少量试点。
38. **无人化故障处置是终极目标**：自动化带来更快执行、更少失误、更可预测的结果，大幅减少琐事（toil）；AI Agent 已能实施安全缓解并在成熟后协助更复杂的中断处置，把工程师解放出来应对真正的架构挑战。
39. **结语**：用户对可靠性与韧性的预期是最终衡量标准；每次韧性改进都是微小而持久的架构改善，跬步千里、聚沙成塔，这就是投资韧性如何不断拓宽组织可靠性边界的真谛。

## 量化数据速览

- 五个九（99.999%）是许多组织务实的 SLO 上限；训练有素地忽略剩余 ~0.001% 故障需极谨慎
- 配置 X 容量的系统在 10X 流量冲击下应继续提供接近 X 的服务能力
- 降级响应示例：仅耗费 20% 的计算量即可达到 80% 的响应质量
- 全局部署示例：2 区域 × 各 2 可用区，单可用区瘫痪最多损失 25% 全局容量；每区域仅 1 个可用区时风险升至 50%
- 假设 RTO 24 小时：若无法在时限内补齐容量并恢复，实质等于承受接近零的 RTO 承诺

## 方法论与流程速查

| 方法 | 步骤要点 |
|---|---|
| 低概率高影响风险排序 | 自己遭遇过 → 他系统遭遇过 → 行业公认可能 → 已知未知（known unknowns） |
| 变更敏感度四级 | 常规 → 中等（推迟高风险变更）→ 高（仅限影响极小或价值极高）→ 极高（暂停一切选择性变更） |
| 故障域恢复四步 | Isolate 隔离 → Repair 就地修复 → Reassemble 重新组装 → Reach 触达并逐个拉回 |
| 事故模式三级 | 正常（标准工具）→ 紧急（低依赖回退）→ 灾难（零依赖组件＋精专团队） |
| 响应 CUJ 八类 | comms / imag / dash / reach / doc / priv / dbg / fix |
| 付诸实践五步 | 制定评估准则 rubric → 从最应防范处入手 → 排查不可消除的依赖 → 对齐业务优势 → 区分绿地与棕地 |

## 实践要点

- [ ] 为自己的组织定义一套韧性与可靠性原则及配套指导规范，把工程精力聚焦于常见风险归类
- [ ] 用技术手段（指标、平台默认配置、代码化强制）落地制度，而非只发文档
- [ ] 每项变更渐进式发布、控制并发：二进制与数据更新独立推进，先单可用区再逐步扩展
- [ ] 新功能一律配特性开关，并保持开关卫生（flag hygiene）；为高风险变更准备紧急刹车
- [ ] 用系统定义（配置文件）自动生成依赖表征，机制上限制可引入的依赖并违规告警
- [ ] 定期验证"可选依赖"真的可选：注入故障时关键功能不得产生任何新告警
- [ ] 评估并记录每个组件跨故障域的分布；扩展时优先增加可用区而非扩大现有规模
- [ ] 过载测试以有效吞吐（goodput）稳定为准：观察负载渐进增加时系统何时失去交付能力
- [ ] 客户端统一使用带抖动的指数退避与自适应节流库，重试严格限制在单层内
- [ ] 为关键数据（元数据、加密密钥）建立与主系统不共享命运的独立降级备份

## 案例速览

- **CASI 金丝雀分析服务**：自动监控正在变更的各副本健康度（CPU/内存增长、错误异常、进程崩溃、探测器结果），足够多副本证明变更安全后才标记为 live
- **Google 值班运维隔离**：值班团队分两个分片错时轮值，每系统每分片配主副两名值班员——轮休间隙突发不可用时仍具备韧性
- **数据中心断电演练**：数据中心团队与 SRE 团队联合应急演练，在受控但绝对真实的环境下对真实集群执行重启
- **Google Chat 故障的混合模式**：仅启用备用沟通工具（IRC/蜂窝直拨），其余响应能力保持正常模式
