# 第4章 · SRE 的文化土壤

> [!INFO] 出处
> 《SRE：Google 运维解密（第2版）》第Ⅱ部分 · 第4章 · 撰稿：Ayelet Sachto、Brian Kudzia、Igor Oks、Jennifer Petoff、Luca Cervasio、Nathen Harvey、Roman Seibel（合著：Garret Holthaus）

**一句话概括**：论证"第五个 9 是人"——工具与流程之外，以可靠性为中心的文化才是把系统可用性抬升一个数量级的决定因素；本章借 DORA/Westrum 实证研究给文化"定坐标"，并用棕地/绿地两条路径把文化培育变成可执行的动作。

## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 组织文化 | Organizational Culture | 团队围绕可靠性形成的共享信念与日常行为模式；决定 SRE 转型长远成败的基石 |
| Westrum 组织文化类型学 | Westrum Organizational Culture Typology | 按信息流动与处理方式分三型：权力导向（病态）、规则导向（官僚型）、效能导向（生机型） |
| 生机型文化 | Generative Culture | 高度协作、信使受培训、失败引发探究、推行新想法、共担风险；可预测交付与运维效能 |
| 心理安全感 | Psychological Safety | 相信提出想法、疑问、担忧或指出错误不会遭到惩罚或羞辱（Amy Edmondson） |
| 预设善意 | Presumed Positive Intent | 假定同事兼具胜任力与可靠品质；一次冲突通常需 5~7 次积极互动来弥补 |
| 无指责事后总结 | Blameless Postmortem | 聚焦系统与流程缺陷而非追责个人的复盘机制，是学习文化的核心实践 |
| 归责意识 / 公正文化 | Just Culture | 承认指责是本能，转而探究"当时的行动为何合理"，同时坚守工程标准 |
| 错误预算 | Error Budget | 系统可容忍的故障风险限额，调和快速创新与稳定可靠的矛盾 |
| 错误预算策略 | Error Budget Policy | 成文的预算处置约定：预算耗尽即放缓/暂停功能发布、转向可靠性建设 |
| SLO 门禁发布 | SLO-Gated Release | 由错误预算余量而非固定日历决定是否发布 |
| 棕地 / 绿地 | Brownfield / Greenfield | 在现有服务上演进可靠性 / 从立项第 0 天起注入可靠性 |
| 信心基准 | Confidence Baseline | 用锚定量表自评完成文化相关任务的信心，以低琐事方式度量文化现状 |

## 关键论点

1. **第五个 9 是人**（Trisha Weir）。流程和工具能把可用性推到 99.9%，再往上，人的行为、协作与底层文化才是达到并维持超高可靠性的要素——成熟组织可实现整整一个数量级的跃升。
2. **可靠性文化有两个基本层面**：以用户为中心（度量必须紧扣真实用户体验），以及把可靠性视为组织层面的核心价值（从一线到高层都认可，并在重大决策中给 SRE 发言权）。
3. **文化靠行为塑造，不靠说教**：学习带来信心，信心驱动行为，行为日积月累塑造文化；用行动带动新的思维方式，远比靠愿景换取新的行动方式容易。
4. **DORA 实证：文化是效能的预测指标**。高信任、鼓励学习与协作的文化是软件交付与运维（SDO）效能最显著的预测指标之一，同时带来更高工作满意度与更低职业倦怠。
5. **无指责不等于无标准**。归责意识追问"考虑到当时的环境、已知信息与压力，这样做为何是合理的"，从系统层面找根因；但对窃取数据等恶意行为仍须问责，并借最小特权、审计与复审堵住红线。
6. **赋能要落到机制**：人人有权提交代码修复（过 Code Owner 评审即可入库）；SRE 可自主调节运维负载——协商暂缓功能发布，极端情况下把寻呼机退还研发团队。
7. **错误预算把价值观变成日常决策**：预算充裕则自信推进部署，耗尽则是放缓节奏、转向可靠性的明确信号；SLO 门禁发布取代"每两周周二发布"式的固定节奏。
8. **落地三道坎**：高管自上而下的支持（含决策授权与不搞事故追责）、契合场景的工具体系（选错工具就采不到正确信号）、预期管理——100% 可靠性是错误目标（Ben Treynor Sloss），没有一键捷径，也不会一劳永逸（每年至少复审一次 SLO）。

## 值得记住的数字

- **1.4 / 1.8 / 3.5**：精通 SRE 实践的团队报告更高 SDO 效能的概率是其他团队的 1.4 倍、报告更佳业务成果的概率是 1.8 倍；拥有高质量文档的团队落实 SRE 实践的概率高 3.5 倍（DORA）。
- **5~7 次**：弥补一次冲突造成的信任损伤，通常需要至少这么多次积极正向的互动。
- **+23 ~ +49 pp**：SRE EDU 入职培训相比普通开发者入职培训，在可靠性相关自评信心上的领先幅度；"利用监控与告警理性决策"一项在 6 个月后仍保持 +43 pp。
- **50% / 20%**：为可靠性工作预留工程精力的常见指引比例；初期哪怕只固定 20%，也足以建立平衡。
- **99.5% vs 99.999%**：当前可用性只有 99.5% 就把初始 SLO 定到 99.999%，无异于自寻死路；把每套系统都维持到 4 个 9（30 天内停机少于 5 分钟）既困难又代价高昂。

## 方法论速览

**信心基准评估文化（四步）**：定义调研问题 → 锚定评分标准（五分制锚定量表：完全不知从何下手 / 他人协助可完成 / 查文档独立完成 / 凭记忆独立完成 / 凭记忆指导他人）→ 在培训前、刚结束、1 个月、6 个月四个时点持续追踪 → 分析并对比结果。问题全部以行动为导向，如"阐明无指责事后总结文化的收益""使用 SLO 与错误预算衡量服务与业务目标的一致性"。

**因材施教（三类受众）**：变革好奇型（新员工，常问"我们为什么这么做"）、变革抵触型（对新工作方式持疑，最想知道"这对我有什么好处"）、变革倡导型（有深厚经验的新人，适合讲成功故事带动他人）。

**棕地演进（七步）**：跨职能合堂培训建立共识 → 选择切入点（业务关键或痛点、团队有投入意愿、能插桩代码）→ 用成熟度矩阵定位现状、以关键用户旅程（CUJ）定义 SLI → 开展"可靠性是否够用"的关键对话 → 制定简明、切合、达成共识的初始 SLO → 引入无指责事后总结 → 展示阶段性胜利并持续迭代。

**绿地设计（三步）**：把 SLO 当作系统设计的输入条件（99.99% 的目标会促使放弃单宿主架构）→ 围绕达标 SLO 展开技术选型、架构模式、埋点度量和面向可靠性的测试 → 从第一天建立运维就绪状态（自动化 CI/CD、运维手册与应急预案、前瞻性容量规划）。

## 实践要点

- [ ] 用"当前可靠性是否够用、不够的代价是什么"的业务对话，替代监控仪表盘的罗列轰炸
- [ ] 给事后总结流程本身设 SLO（撰写/评审/发布时限），并追踪：无有效行动事故占比、人工发现事故占比、单次事故寻呼次数比率
- [ ] 追踪生产环境手动变更频率，并努力让它趋近于零
- [ ] 用五分制锚定量表，在培训前/刚结束/1 个月/6 个月测信心，为文化做低琐事基准
- [ ] 棕地试点选业务关键、团队愿意投入、且能插桩代码的服务，从"足够可靠"倒排差距
- [ ] 初始 SLO 只聚焦两三个关键 SLI，立足当前实际表现
- [ ] 制定成文的错误预算策略；预算耗尽默认放缓发布，紧急修复要显式讨论代价
- [ ] 用 SLO 门禁替代固定节奏发布；产品与工程以错误预算为共同沟通依据
- [ ] 保护可靠性专项时间（初期 20% 即可），预算充裕时投向自动化与长线项目
- [ ] 向高管争取支持时用 DORA 证据说话：文化预测效能、业务成果与员工福祉
