# 第7章 · SRE 协作模式

> [!INFO] 出处

## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 协作模式 | Engagement Model | 双层含义：SRE 与研发协作的流程；为提升服务可靠性而提供的各项服务 |
| 生产就绪评审 | Production Readiness Review (PRR) | Google 早期二元化协作的准入把关流程，耗时数个季度 |
| 基础支持服务 | Foundational Offerings | 伙伴关系内所有服务均可享用的可扩展能力：事后总结评审、开放答疑时间、应急事件响应团队（IRT） |
| 成果 / 攻坚项目 | Outcome / Effort | 工程攻坚要达成的可靠性目标 / 完备的软件工程项目；并行攻坚项目应严格限于少数几个 |
| 海勒姆定律 | Hyrum's Law | API 用户足够多时，系统所有可观察行为都会被某些人依赖 |
| 核心旅程 | Critical Journey | 企业级场景下无法穷尽监控业务逻辑时，聚焦的关键行为子集 |
| 运维手册 | SRE Playbook (Azure) | Azure 将 SRE 落地方法体系化而成的《运作手册与运作模式》 |
| 死守寻呼机 | Paging Patrol | 反模式：SRE 接手轮值后被迫长期承担日常生产维护、替研发兜底 |

## 关键论点

1. **协作模式的三层作用**：定义职责、流程与原则并管理双方预期；决定 SRE 精力投向何处的工作选择机制；提供书面参考以减少误解、化解冲突。注意与第6章的心智模型区分——组织架构关注汇报关系与资金来源（谁为 SRE 买单），协作模式关注工作契约（做顾问咨询，还是接手寻呼机值班）。
2. **成熟度看三个维度**：初衷（响应型→专职型→融入型）、影响（深度优先 vs 广度优先）、价值（战术→优化→战略）；SRE 须与业务成果对齐才能发挥最深远影响。
3. **七种协作范围各有取舍**，成熟组织混合采用并动态调适——静态僵化的划分会让团队逐渐偏离产品真实需求；业界最常见的"大包大揽"式更名最危险，很多组织的技术革新在改完名字那一刻就戛然而止。
4. **消费端与企业级的根本分野是客户关系**：企业级场景下单一个大客户的信任与任何 SLO 同样关键，即使指标全部达标也须对个别客户异常紧急响应。
5. **分层模式的最大问题是以轮值为核心**：讨论被框定在"谁背寻呼机"，全面支持被视作"最好的待遇"，反而强化了"SRE 首要职能是值班护航"的固有认知——而待命只是手段，单纯以 SRE 待命为协作核心是反模式。
6. **超越 PRR 的方向是平台化与赋能**：把最佳实践固化进平台与工具，让服务"设计之初即生产就绪"（production-ready by design），SRE 只深审高风险上线。
7. **Azure 与迪士尼的共同启示**：把探索历程固化为书面、可复用、数据驱动的方法，是最有力的规模放大器。

## 协作成熟度：初衷、影响与价值

- **"如何做"——初衷（intent）**：响应型（Reactive，先求眼前稳定的"救火"，是务实起点）；专职型（Specialized，构建杠杆效应与可复制的成功模式）；融入型（Integrated，让产品默认可靠并以此为商业竞争优势）。
- **"做什么"——影响（impact）**：深度优先（全神贯注单项事务的可靠性，能力精湛但范围聚焦）；广度优先（覆盖整个生态、识别跨组件的系统性风险）。SRE 应当时刻"环顾左右"，这是深耕单系统的研发人员难以做到的。
- **"为什么做"——价值（value）**：战术层级（"确保服务持续运行"）→ 优化层级（"投入在哪里能产生最高业务影响"）→ 战略层级（直接对齐业务成果，如"如何衡量并提升整个客户旅程的可靠性"）。

## 划定协作范围：七种模式

| 模式 | 做法 | 优势与风险 |
|---|---|---|
| 大杂烩（Kitchen Sink） | 第一支/唯一一支 SRE，职责漫无边界 | 充当纽带、催生标准；但易过载、琐事缠身，蜕化回传统运维 |
| 嵌入式（Embedded） | 派驻研发团队内部，深度参与代码与配置 | 言传身教、见效快；但孤立闭塞、缺跨队规范，适合初创期 |
| 产品/应用 SRE | 聚焦某一关键产品领域 | 聚焦清晰、与业务优先级挂钩；缺统一平台时重复建设、沦为信息孤岛 |
| 基础设施 SRE | 维护共享基础设施与统一生产平台（即现代平台工程团队） | 高度专业化 + 广度优先影响；须防与遗留托管环境过紧耦合 |
| 工具团队 | 构建衡量、维护与提升可靠性的软件 | 摆脱被动救火；但工具脱离一线痛点则南辕北辙、反增琐事 |
| 咨询顾问 | 阶段性建议与指导（定 SLO、做 PRR、Office Hours） | 跨大范围放大影响力；风险是缺业务上下文、"光说不练、隔靴搔痒" |
| 混合模式 | 按应用与团队定制组合，并可设首席可靠性官（CRO） | 兼采众长；需定期重审、按应用成熟度与业务阶段动态调整 |

既有服务架构的本质特征也会左右选择：少量高度定制的单体服务倾向垂直整合的产品型 SRE，高度标准化的微服务环境更适合重用基础设施团队。

## 面向消费端与企业级产品的 SRE

| 维度 | 消费端产品 | 企业级产品 |
|---|---|---|
| 用户与收入 | 数百万至数十亿用户可自由转向竞品，按利润率与规模优化 | 采购周期长、大额合同集中，生存依赖留住关键大客户 |
| SLO 与错误预算 | 更为有效；可辅以搜索趋势、社媒舆情作补充信号 | 单一客户问题须按重大中断响应；隐性保证难入 SLO，聚焦核心旅程，并把技术支持工单（Support Case）纳入应急发现信号 |
| 应急事件管理 | 止损速度第一，按受影响用户比、流量与营收指标定紧迫度："先止损恢复，后排查根因" | 中断定义更主观；"先通报客户，后推进止损"，全程透明沟通进展 |
| 缓解措施 | 重启、扩容、迁移通常有效；按用户分片、优雅降级 | 常见手段多失效（客户已依赖新行为，贸然回滚有风险）；需手术刀式精准方案，治本之策是架构上物理隔离大客户 |
| 系统设计 | 故障域对最终客户完全隐蔽 | 暴露面向客户的故障域，客户可能自建兜底系统 |
| 团队组织 | 按客户体验或服务边界灵活划分 | 紧贴客户体验对齐（如把身份认证与访问相关服务整合），而非按底层服务分组 |

两类产品亦有共性：都与研发建立紧密伙伴关系，都提供 SLO 与应急事件管理等基础工程服务，都致力于限制爆炸半径、改进变更管理。

## Google SRE 协作模式的演进

**早期：PRR 准入制**（2003 年起步时仅 7 名工程师的"大杂烩"）——二元化：要么获得整套 SRE 职责打包交付（轮值待命、事后总结、系统设计支持、监控、自动化、发布工程、容量规划），要么研发自行"谁构建、谁运维"。接入服务须从研发向 SRE 划拨编制，促使研发设计更简单健壮的服务、降低总拥有成本（TCO）；PRR 历时数个季度，产出 SLO、削减告警工单、运维文档、渐进式发布、备份恢复、容量规划、守住故障域等改进清单。固有缺陷是"黏滞难脱"（sticky）：接入后难抽身，运维占比递增、知识沉淀在 SRE 侧使研发无法自给自足，且 SRE 常在生命周期后期才介入，架构改造代价已高。

**分层协作模式**——基础层（Baseline，咨询/培训/临时支持，无需专门编制预算）、协助层（Assisted，SRE 项目专项 + 部分共担轮值 shared on-call，适合新服务早期）、全面层（Full，完整 SRE 能力体系）。初衷是让服务在层级间流畅升降级、让 SRE 在生命周期早期这一黄金时期介入；但实践中层级迁移的繁琐程度不亚于旧的接入与退出，且模式仍以轮值为核心（见关键论点 6）。

**成果导向模式**（2025 年正式推广）——在业务伙伴关系（partnerships，通常覆盖一个产品领域及其 SRE 团队群）层级统筹编制与预算，终结事务性博弈；基础支持服务人人可享、无需长期承诺，可按需灵活介入而不陷入粘滞承诺；绝大多数工作围绕成果（outcome）组织，并行攻坚项目（effort）严格限制在少数几个并附大致时间表以防粘性协作；跨伙伴关系的众多服务若需相同成果，是组建基础设施 SRE 团队、把方案固化进生产平台的强烈信号。

## 案例研究：Persistent Disk 的成果导向协作

- **旧模式（2023）**：半嵌入式（semi-embedded）——无专职 SRE 经理，团队按轮值人力需求搭建，成员各自对接特性研发团队；TL 身兼咨询、PRR 与多项目技术指导而不堪重负；研发难以说清 SRE 到底负责什么（"监控"被解读为"所有监控工作"）；士气低迷，成员自认研发的附庸。
- **演进**：调研找准症结并争取高层支持；先界定基础保障服务（事故应急响应团队、响应 SLO 告警、接管全球地域扩展 geo-expansion）；再明确四个核心成果——缩短事故检测/排查/沟通/恢复耗时、定期演练可重复的容灾策略、消除最主要运维负载以降本、重构部署体系提升发布与回滚效率；按成果划分四个小组，TL 以工程项目形式撰写技术战略与路线图，据此重新协商运维与值班分摊，OKR 围绕成果进展设定。
- **成效**：初期有抵触（研发已习惯嵌入式 SRE 代劳告警配置，SRE 以一项告警工程改造化解），随后工作过载明显减少、TL 回归核心事务、辅导与发展机会增多、双方预期清晰、伙伴关系显著改善。

## 案例研究：微软 Azure 模式

- **演进**：2015 年雏形约 40 人，以产品级协作项目起步（Azure Resource Manager、Azure SQL）；意识到"整体的力量大于部分之和"后探索横向切分、跨队贯通；2022 年底 SRE 成为新成立的 Azure 可靠性团队（Azure Reliability）核心支柱，使命是将 Azure 打造为业界最可靠云服务商。
- **Azure SRE Playbook**：三原则是伙伴关系为根基、数据驱动且带鲜明技术主张的结构化路径、以 SRE 与研发高管共同签署的 KPI 对齐顶层质量目标。六阶段运作（每阶段附 KPI，达"足够好"即推进）：①服务基石（依据安全未来倡议 SFI 与卓越质量倡议）→ ②服务健康度与安全部署实践 SDP（关键用户旅程与 SLO、分阶段灰度发布）→ ③运维效率（TTx 指标取第 75 百分位，兼顾右尾并剔除极端值）→ ④发布与变更管理（DORA 四项指标中的三项）→ ⑤降低可靠性风险（定期风险威胁建模）→ ⑥可扩展性与容量（可预测、自适应的容量规划）。
- **扩展与 ROI**：三种扩展模式——通用基础设施（依托 AKS、Service Fabric 等标准化平台）、横向能力（如 Service Health SRE 改善全 Azure 的 SLO、Change SRE 让每次变更更安全）、标准规范左移（IDE 与持续集成中提前检测故障模式）。组织发展至约 200 名 SRE；纯财务折算不足以体现价值，更具说服力的是事业部级质量 KPI——获得 SRE 支持的服务改善速度始终明显更快；最有力的论证并非节省成本，而是有无 SRE 支持在质量与可靠性上的切实差异。

## 案例研究：迪士尼全球 SRE

- **组织形态**：中心化的可靠性专家团队深度嵌入各业务单元，扮演长期可靠性合作伙伴而非工单驱动的共享服务；协作关系延续数年，产品更迭时顺势转型而非就此终止，从而积累组织级知识（institutional knowledge）。
- **嵌入式与集中式并举**：嵌入式让 SRE 从"事务型"（工单队列、吞吐量）走向伙伴关系型——"贴近催生同理心。同理心建立信任。信任加速交付步伐。"以轻量级协作协议固化四问：正在保障哪些业务成果？哪些可靠性风险构成威胁？"足够可靠"意味着什么？如何衡量成功（SLO、错误预算、就绪里程碑）？集中式则以企业级全局视野识别跨团队共性模式、沉淀规范标准、建设共享工具平台、统一培训与职业路径——典型如声明式基础设施与 IaC 转型：集中团队定参考架构与工具，嵌入式 SRE 因地制宜落地。
- **轮值组织**：On-call 是衡量系统健康状况的晴雨表而非默默承受的负担；构建系统的团队理应承担运维，SRE 以提升告警质量、理顺升级路径、消除琐事，协助团队设计可持续的轮值模型。在线产品联合排班；COTS 场景由 SRE 接管并重度自动化；乐园设施上线后交本地工程团队；媒体内容管线由 SRE 保平台可靠性。SRE 绝不应充当长期兜底，痛点持续存在即被视为反馈信号。
- **最痛的教训**：某次协作中业务单元管理层更迭、转向传统 IT 运维模型，SRE 团队未及时洞察并转向或退出，反而加大投入试图说服，最终草草收场、两败俱伤——步调一致绝非一劳永逸的单次协议；"不要去未曾邀请你的地方。"

## SRE 如何与合作伙伴协作

- **与产品管理**：SRE 应成为非功能需求（可用性、响应时间、吞吐量、成本效益、数据完整性）的倡导者，以客户流失率、资金损失等指标建立与业务结果的关联共识；理想情况下由产品经理凭其对用户需求的洞察主导 SLO 定义；定期向产品管理同步故障影响，事后总结可以产品管理团队为目标受众。
- **服务生命周期协作**：设计阶段介入效果最佳；尽早定义 SLO 尤为关键——99.99% / 10 ms 与 99% / 250 ms 的服务底层设计本质不同；在一线工程师与团队负责人两个层面保持定期沟通，防止"责任分散"（diffusion of responsibility，人人有责等于无人负责）；指定能提供技术领导力的服务 TL 统筹长期方向；运维与待命共同分担（共享排班、互为升级、或 SRE 管基础设施故障而研发管应用故障）；警惕"死守寻呼机"反模式——把服务交还研发时须周全计划与明确时间表。
- **超越生产就绪评审**：PRR 易让 SRE 沦为"守门人"，工作量随功能线性增长，且评审常在上线前不久才暴露重大架构问题；转向路径是投入具有明确设计主张的生产平台、推进发布自动化与标准化、横向监控与自动回滚，SRE 只深审复杂高风险上线，常规上线轻量评审乃至由研发自行完成。
- **影响力扩展三法**：以答疑时间（office hours）提供临时指导；以培训分享与案例研究共生生产专长，拒绝做"人肉抽象层"；以环境简化、标准化架构与自动化强制规范，从根本上降低对 SRE 协作的依赖。

## 实践要点

- [ ] 用初衷/影响/价值三个维度定位自身 SRE 组织的现状与目标层级
- [ ] 定期重审职责范围，按应用成熟度动态调适；警惕"换汤不换药"式的更名改革
- [ ] 企业级场景：支持工单纳入应急发现信号、聚焦核心旅程；对大客户实施架构级物理隔离以便定制缓解
- [ ] 设计协作模式时勿以"谁背寻呼机"为核心；待命只是收集一手信息的手段
- [ ] 推行成果导向：并行攻坚项目限制在少数几个，并附大致时间表防粘滞协作
- [ ] 多个伙伴关系出现相同成果诉求时，组建基础设施 SRE 团队并把方案固化进平台
- [ ] 与产品管理深度协同：设计期共同迭代 SLO；事后总结写给产品团队看，聚焦业务影响
- [ ] 与管理层的一致须持续维系；邀请失效时体面转向或退出，不做长期轮值兜底
