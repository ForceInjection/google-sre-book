## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 测试金字塔 | Test Pyramid | 单元→集成→系统→韧性测试的分层模型；体现的是依赖层级而非价值层级，"测试金杯"等现代模型更强调 TIP 与金丝雀 |
| 生产环境测试 | Testing in Production (TIP) | 以受控方式直接在生产环境验证变更，用严格受限的用户损害换取最贴近真实的反馈 |
| 密封测试 | Hermetic Testing | 不发起网络调用、输入完全确定的隔离环境中运行测试，降低"朝三暮四"的调试困惑 |
| 配置四不变量 | VOIS | Versioned / Observable / Independent / Safe：配置至少要与代码受同等关注的四大特性 |
| 配置漂移 | Configuration Drift | 生产实际状态与代码库中已提交状态脱节，直接违反 VOIS 的 Safe 要素 |
| 金丝雀测试 | Canary Testing | 少量服务器先升级进入"孵化期"（baking the binary），承接生产流量并严密监控后逐步扩大 |
| 金丝雀分析 | Canary Analysis | 程序化对比新旧样本群体的 A/B 统计检验；默认规则覆盖崩溃与 RPC 错误等常见风险 |
| 容灾演练 | DiRT | Disaster Recovery Test：强调在生产环境采取实际行动并实战验证的业务连续性演练项目 |
| 以客户端为中心的变更监管 | Client-Focused Change Supervision | 版本元数据随 RPC 传播、客户端导出归因指标，捕获只在上下游服务暴露的退化 |
| 故障注入 | Fault Injection / Chaos Engineering | 以安全可控的方式蓄意破坏系统，主动探索失效空间（failure space），无需等事故上课 |
| 形式化方法 | Formal Methods | 用数学严格建模系统行为并证明性质；验证器分模型检查与定理证明两大阵营 |
| 判定基准问题 | Oracle Problem | 传统测试难以判定输出对错；形式化规约可对任意给定输入给出精确判定 |
| 基于模型的测试 | Model-Based Testing (MBT) | 依托形式化模型算法化生成测试用例，大幅提升覆盖率与效率 |
| Agent 式测试 | Agentic Testing | 面向 AI Agent 软件开发的三层测试：经典软件、生成内容、工具使用 |
| 致命三要素 | Lethal Trifecta | 访问私有数据 + 不可信内容 + 外部通信，Agent 工具使用层面的安全焦点 |

## 关键论点

1. **测试是模型的替代品**：测试的真实作用是度量你对现实世界（心智模型与系统性模型）的理解有多不准；软件 bug 只是模型误差的一部分，软件所依赖的各项假设本身就是故障的重要诱因。
2. **金字塔体现依赖层级，不是价值层级**：集成测试往往比单元测试更具价值；层级越往上，复杂度越严苛，实际耗费的物理时间与资源也越急剧攀升。
3. **配置与代码同等危险**：一次随率的 `terraform apply` 即可让基础设施变更立即生效，Google 多起公开大故障均由配置引发；VOIS 框架（版本化、可观测、独立、安全默认）是底线。
4. **监控与测试一体两面**：测试就是面向预发布阶段的监控——把监控系统的告警先决条件转写为测试用例，可在生产环境触发前验证应对能力，还能在排障假设分析中抢占先机。
5. **金丝雀的价值在于真实用户行为**：生产环境把软件概率性暴露在建模时未曾考虑的条件下；用户行为既受模型引导又反过来影响模型，因此机器学习服务的金丝雀测试尤为重要。
6. **DiRT 成功的三件事**：把演练视为技术与组织双重实践而非合规活动；贴合各团队自身优先级而非自上而下强推；持续内部宣传可靠性的核心价值。
7. **故障注入化被动为主动**：复盘天然滞后于故障暴露；用"工作流 X 能抵御故障 Y（以 Z 度量）"的范式主动模拟网络瘫痪、资源耗尽与进程崩溃，无需等生产环境用事故来上课。
8. **归因指标让问题立刻暴露**：前端报错而后端看似正常时，只有把"每个请求途经的后端版本"纳入指标，发布事故才能被迅速发现并阻断——版本 222 的高错误率一目了然。
9. **形式化方法要务实落地**：Google 放弃"要么全有要么全无"的学术路线，把验证应用于特定子组件（P4-BAR、TPU 硬件、Fiat Cryptography、Tricorder），所得保障反而远胜包括生产测试在内的其他形式。
10. **Agent 时代测试分层递进**：第 N+1 层的故障很难用第 N 层的方法检出——模型谄媚倾向测不出来，工具回归缺陷也逃不出评测集；生成式 AI 反而让受控的生产环境测试有望成为主要手段。

## 测试类型速览

| 测试类型 | 作用域 | 要点 |
|---|---|---|
| 单元测试 | 同一代码库内的函数 | 最细粒度、数量庞大、随每次代码变更快速运行 |
| 集成测试 | 跨单个代码库 | 用依赖注入（如 Dagger）与受限的轻量级 Mock 替换外部调用 |
| 系统测试 | 跨其他软件系统 | 验证端到端功能；子类型含冒烟（happy path）、性能、回归 |
| 韧性测试 | 跨组件/外部依赖 | 即混沌工程，直接模拟基础设施与代码故障；故障注入属于此类 |
| 生产测试 | 生产环境 | 测试软件在生产环境中的真实特性，与密封测试理念相反 |
| Agent 测试 | 编写软件的 Agent | 改进并指导基于 Agent 的软件开发 |

## 服务级韧性测试维度（DiRT 衍生的分类框架）

| 维度 | 典型测试 |
|---|---|
| 容量与稳定性 | 节点宕机、冷启动、紧急扩缩容/上线时的表现 |
| 数据韧性 | 备份恢复、损坏数据识别、跨区/跨可用区复制一致性 |
| 基础设施韧性 | 网络劣化、隔离分区、数据中心断电/制冷、硬件资源耗尽 |
| 依赖项韧性 | 第三方故障或降级、依赖项降级时仍达成目标、SLO 临界状态下运行 |
| 故障处理与恢复 | SPOF 故障转移、回滚速度、错误与脏数据容忍（Fuzz 测试） |
| 运维韧性 | 应急事件管理演练、预案执行与验证、紧急配置变更、发布回退 |
| 业务/人员/安全 | 关键业务流程连续性、关键人员缺勤、工具链损坏、恶意中断 |

## 以客户端为中心的变更监管：方案与收益

- **基础方案**：让所有作业在 RPC 响应中附加版本元数据，客户端追踪出站 RPC 并递增归因指标计数器——两端改动均实现为 RPC interceptor，服务只需引入拦截器即可导出把控发布闸门的度量指标。
- **多跳场景**：为响应扩展信息中的每个版本附加 TTL 逐跳递减，或按服务逻辑分组携带归属元数据，确保版本数据可透传到达任何地方。
- **数据利用**：所有指标汇聚于时序监控数据库 Monarch，每日流水线生成"服务端-客户端"映射关系，自动为金丝雀分析生成检查规则。
- **代价与挑战**：每个 RPC 注入元数据与拦截器执行都有开销；归因指标基数极高（某些服务单指标时间序列超过 5000 条），须审慎选择标签并持续监控基数。
- **Google 收益**：内容安全平台允许各客户端自定义归因指标并集成进发布分析；某后端变更曾导致某客户端 99% 的内容被误标记为违规（正常仅 1%），靠变更监管在波及用户前成功阻断发布。

## Google 的形式化方法实践

- **P4-BAR**：以 P4 作为规约语言自动验证 SDN 交换机转发行为——建模、基于模型的测试输入生成、与仿真系统差分测试三步走；自 2020 年以来发现 300 多个独立互异的转发缺陷。
- **硬件设计**：TPU 等自研硬件在设计周期早期引入形式化验证，在物理实现前发现协议违规、死锁与极端场景功能异常。
- **Fiat Cryptography 与 BoringSSL**：自动生成高度优化的加密代码，在生成的同时给出数学正确性证明，从根源消除实现层漏洞。
- **Tricorder、Clang-Tidy 与 Clang Static Analyzer**：静态分析平台深度集成代码评审与 IDE；符号执行与抽象解释挖掘路径敏感的深层 bug。

## 实践要点

- [ ] 测试计划写明目标、执行方式、监控手段与成功判据，附详细回退（backing out）方案，所有脚本经同行评审
- [ ] 为紧急发布留"测试后台追"通道：把抢推事件与待测事件关联，失败结果尽快反向标注，避免陷入未经测试推送的恶性循环
- [ ] 配置全面实践 VOIS；用 `--dry-run`、合并前测试或自动调谐防配置漂移，切勿对告警噪声习以为常
- [ ] 按异常驱动测试：为每个已上报且修复方案可验证的 Bug 编写"先失败后通过"的用例
- [ ] 审视监控告警的先决条件，把它们转化为集成或系统级测试用例（如 Mock 依赖按错误率返回响应）
- [ ] 金丝雀起步承载数量级递增流量（如 0.1% 起，低流量区渐进、高流量区 10%→50%→80%→100%），先启用崩溃与 RPC 错误的默认分析规则
- [ ] 故障注入从"工作流 X 抵御故障 Y 以 Z 度量"起步，优先低频的单非关键组件；生产环境测试务必部署防护措施
- [ ] 依赖项测试用核心层注入（Mock 返回错误/超时/504）验证弱依赖属性与 SLO 缓解措施，测试后清理残留
- [ ] 归因指标严控标签基数并随规模增长持续监控；两条 RPC 属性即可让指标基数成倍增加
- [ ] 对核心算法与控制循环引入 TLA+/模型检查；Agent 生成的代码固定提示词与温度参数，用 golden eval 集与基准评估捕捉漂移
