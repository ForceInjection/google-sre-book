## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 事故因果模型 | Accident Causality Model | 关于"事故因何发生"的认知与信念体系，决定了事后分析的视野与改进方向 |
| 线性事件链 | Linear Chain of Events | 传统模型：事故是组件失效事件的先后序列，首个事件被定为根因，配套纵深防御（Defense in Depth）逐环设防 |
| 根因诱惑 | Root Cause Seduction | 为复杂事故寻找单一简单解释的本能倾向；促成因素（Contributing Factors）往往根本无法串成一条链 |
| 系统理论事故模型和过程 | STAMP (System-Theoretic Accident Model and Processes) | 现代因果模型：事故归因于未能对组件行为施加安全约束的系统设计；因果因素是影响人或软件决策的系统性因素 |
| 系统理论过程分析 | STPA (System-Theoretic Process Analysis) | 基于 STAMP 的前瞻性危险分析，仅凭纸面架构即可开展，在事故发生前识别并消除系统性缺陷 |
| 基于系统理论的因果分析 | CAST (Causal Analysis based on Systems Theory) | 基于 STAMP 的回顾性事故分析：把目标从"寻找故障部件"转向"查明整个系统为何未能阻止事故" |
| 不安全控制行为 | UCA (Unsafe Control Action) | 在特定上下文中可能导致危险状态的控制行为：未执行、过早、过晚、持续时长不当或做了错误动作 |
| 危险状态 | Hazard State | 可被观测到的系统状态，最坏情况下导致损失，如"发布的地图与现实世界不一致" |
| 分层控制结构 | Hierarchical Control Structure | STPA/CAST 的建模语言：控制器、受控过程与反馈构成的"控制-反馈"循环，Google 内部分析通常只有 5~10 个方框 |
| 心智模型偏差 | Mental Model Gap | 控制器（人或软件）对系统状态的认知偏离真实状态，由延迟反馈、激励错位、培训不足等上下文塑造 |
| 涌现性质 | Emergent Properties | 由组件交互产生、只能把系统作为整体来分析的性质；安全性正是其中之一 |
| 系统性因素 | Systemic Factors | 影响所有控制器行为的顶层因素：安全文化、沟通协调、变更管理、安全信息系统、环境变化等 |

## 关键论点

1. **传统因果模型撑不起复杂系统的事故分析**。线性事件链默认"时间先后即因果"，无法解释事件背后的因果因素；一旦根因牵涉人的行为就容易滑向指责，而纠正措施能否杜绝同类事故，才是检验教训是否被吸取的试金石。
2. **STAMP 的核心转向**：事故不是"某人或某组件失误"，而是系统设计允许了不安全行为滋生；人为错误和软件缺陷只是表象（症状），要防范问题必须把目光投向人与软件共同运行于其中的更大系统。
3. **STPA 与 CAST 是同一枚硬币的两面**：前者前瞻（在纸面设计上预判事故）、后者回顾（查明系统为何未能阻止事故）；都以控制结构为建模语言，都与无指责文化高度契合——探究"为什么当时的决定在当时看来合情合理"，而不是去找责任人。
4. **设计阶段修复缺陷的成本比生产环境低几个数量级**：运维阶段排修可能要整个团队耗时一个月，在设计文档阶段或许一名工程师一个下午即可搞定；STPA 恰好是少数能直接作用于设计文档的 SRE 工具。
5. **STPA 补足了 DiRT 与想象力之间的空白**：灾难性测试受限于"我们能想到哪些场景"，STPA 则系统性揭示设计中的前瞻假设，为测试提供有据可依的场景清单——尤其覆盖"没有任何组件故障、系统却无法达成目标"的情形。
6. **CAST 的改进建议直击系统性、组织性因素**：重构评估流程、重排人员编制、全公司度量改进完成度——这些是头痛医头式事后总结永远开不出的处方。
7. **推广的关键是让价值可见**：一次成功分析加一项"从未有人发现过"的重大缺陷，远胜一小时的抽象方法论宣讲。

## STPA：前瞻预判事故的四步骤

1. **界定分析范围**。识别利益相关方（SRE、开发、公司、客户、最终用户），确定系统总目标与必须避免的损失（losses，含收入、品牌信任与使命损失），再定义危险状态——可观测、最坏情况下导致损失的系统状态。
2. **对系统建模**。构建分层控制结构：把执行同一目标功能的各种结构归并为抽象的控制器，每个控制器携带控制算法与心智模型（过程模型），向下发出控制行为，靠反馈回路更新认知。让 SRE 与产品研发共建控制结构，本身就能消除各方对系统的理解偏差。
3. **识别不安全控制行为（UCA）**。逐一审查每个控制行为，凡在特定上下文中可能导致危险状态的即为 UCA，包括没有执行、执行过早、过晚、持续时长不当。
4. **构建因果场景**。追问控制器为何会采取 UCA：反馈错误或缺失？心智模型偏差？沟通脱节？把场景清单交系统专家头脑风暴补全，排定优先级，再设计能覆盖大片场景空间的工程方案。

## STPA 应用案例：Maps 数据更新审批流程

**背景**：2019 年 Google 将日本地图切换为自主知识产权数据，其间大规模更新了都道府县、市区町村等行政区划要素。更新人员误删地理要素与行政区划之间的关联并依赖每日修复流水线自动恢复：变更被拆成多组小变更序列化提交，仪表盘上"不一致性逐渐下降"不足以令人警惕；而第一组更新恰在每日修复结束后应用——被删关联要到次日才恢复，日本地区的地图搜索在此期间彻底失灵。

团队没有停留在优秀的事后总结上，而是选择运行 STPA（验证前瞻分析能否发现同样缺陷，并摸清危险状态全集），请来 MIT 系统安全工程合作组织执行主任 John Thomas 博士指导，花数周边学边做。

- 步骤 1 意外收获：系统设计假设"不一致性是局部且短暂的、后台常驻修复会兜底"，STPA 访谈发现这一假设从未被验证且被证伪——不一致性涉及海量地理要素、持续可达数周，由此催生了实时度量不一致性的启发式规则。
- 步骤 2 首次为"地理空间数据专员 → 评审团队（审批人 + 领域专家 SME）"的人工审批链路建模——这套关键交互在原事后总结中从未被分析。
- 步骤 3 得到反直觉 UCA：在数据更新未获 SME 批准的情况下，评审团队审批人予以批准。
- 步骤 4 揭示成因：评审团队存在"24 小时内收集反馈、无人异议即批准"的不成文惯例（为应对地图数据新鲜度压力逐渐形成），叠加"任何问题都会被迅速修复""新数据大概率更好"的错误假设；美国评审人周四提交申请恰逢日本节假日，SME 下周才看到——远在美国的审批窗口到期时变更已获批并提交，系统已在危险状态下运行了相当长时间。

**成果与 ROI**：两名工程师兼职加一位专家支持，五周完成；分析 30 多个主要软件子系统、十几支工程团队的交互，识别出 56 个揭示系统缺陷的因果场景，产出 34 条改进建议（事后总结仅 7 条）。STPA 复现了事后总结发现的几乎所有缺陷，而额外发现的缺陷原本可能引发至少四起其他重大事故。

## CAST：回顾性事故分析的五步骤

1. **收集基础信息**。确定损失（losses）与危险状态（hazards），编制按时间排序的初始事件时间线，提出通用性问题（如"为什么只评估了四个州？它们如何被选中？"），全程不追究、不划分个人责任。
2. **对控制结构建模**。把事故视为控制结构失效的结果，对事发时的系统控制结构建模，明确每个控制器与事故相关的具体职责——职责中的混淆或不一致往往直指关键因果因素。
3. **分析各控制器的行为贡献**。预设"每个控制器在当时都是合乎情理的"（Nancy Leveson：指责是人类控制的大敌）；先客观中立地描述"究竟发生了什么"，再解释"为什么会这样"——心智模型偏差与上下文因果因素。控制器是软件时，则审查架构设计及"设计如何确保安全行为"的错误假设。
4. **识别控制结构缺陷**。跳出单个控制器，寻找影响所有控制器行为的系统性因素，常见类别有安全文化、沟通与协调、变更管理、安全信息系统、环境变化。CAST 尤其擅长发现复杂组件交互导致的涌现式缺陷。
5. **制定改进计划**。在组件与控制结构两个层面制定建议；每条建议都可追溯至所应对的因果或系统性因素，并按紧迫性或成本排序。

## 案例研究：城市名称标注错误事故

2024 年，美国城市名称在 Google Maps 上附带了美国人口普查局（US Census Bureau）口径的额外文本（如 "Indianapolis city (balance)"）。传统事后总结给出两个根因：其一，数据采样不完善——评估抽样只覆盖 4 个州（WA、CA、TX、NY），与实际出现错误的 6 个州（MT、KS、IN、KY、TN、GA）零重叠；其二，评估工具链从未考虑检测错误的城市名称。对应建议是自动化检测、格式校验防无效名称入库、编写启用特定检查的操作指引。

CAST 分析则向前多走了几步：按五步骤建模"数据集导入团队 / 地理空间数据专员 / Maps 数据库 / 工程团队"的控制结构；逐一分析控制器行为贡献，例如数据集导入团队的心智模型偏差——"人口普查局是可信数据源""问题均匀分布所以小样本抽样足以代表""工具只能检测大规模问题，于是遗漏了小规模但影响巨大的复合型问题"。最关键的系统性因素是**环境变化**：多年来外部数据集规模经历了非计划性的渐进式增长，现有控制手段逐渐失效——导入策略超出承载能力、退化成易错的人工检查；评估工具的需求规范早已陈旧，把按州拆分的数据集误归类为"小型"，未触发本可当场发现异常的并排对比评估（side-by-side evaluation）。最终改进计划聚焦整个数据导入系统：基于流失率/变更率（churn/change rates）的结构化采样取代随机抽样、为频繁地图实体建立独立探测告警、落实数据提供方通报错误的策略。

一个贴切的比喻：事后总结只能清理桌面上洒出的液体与碎玻璃；CAST 会追问桌子为什么晃、支撑桌腿的控制结构为什么没对齐。

## 为什么系统论与安全工程对 SRE 至关重要

- **"希望不是一种策略"**。SRE 需要把工程投入与业务产出联系起来，主动阻止问题蔓延至用户侧；前瞻性可靠性工程的核心挑战在于系统本身的极度复杂性。
- **为何选择 STPA**：它能比其他方法识别出明显更多的系统缺陷（尤其是复杂交互类）；传统 SRE 技术无一例外始于故障（演练、故障注入、DiRT），STPA 却能覆盖"没有任何组件故障、系统却无法达成目标"的场景；它还能系统化推导监控、告警阈值与可观测性需求，甚至逼出那些"显而易见却从未有人问过"的设计问题。
- **为何选择 CAST**：与传统事后总结相比有两项本质差异——超越事件链与根因，深入左右决策的因果与系统性因素；聚焦系统性因素，使改进计划直接反映组织性本质，直击控制结构顶层的杠杆点。

## 传统 SRE 方法与 STPA/CAST 的对比

| 维度 | 传统 SRE 方法 | 安全工程（STPA/CAST） |
|---|---|---|
| 基本假设 | 事故不可避免，投资监控/工具/培训以便事后补救 | 用 STPA 预判事故，在缺陷引发事故前优先修复 |
| 学习机制 | 事后总结并浅层调查，头痛医头脚痛医脚 | 把系统视作有机整体，事前识别并修复因果因素 |
| 分析方向 | 自底向上，从离散事件归纳通用问题 | 自顶向下，从系统正确运行的前提出发找偏差 |
| 改进目标 | 解决已识别的根本原因，希望杜绝复发 | 消除因果因素与系统性因素，阻止整类事故 |
| 文化 | 无指责事后总结建立心理安全感 | 兼具无指责性与深度分析能力，探究决策背后的深层因素 |

## 推动 STPA 与 CAST 的落地推广

**向组织引入 STPA**：

1. **价值叙事要具体**。15 分钟的推广介绍容易显得像自圆其说的灵丹妙药；真正的卖点是"在设计阶段应用它带来的巨大 ROI"——设计缺陷修复的机会成本随发现节点后移而急剧攀升（改编自 2018 年 SEI 报告与 John Thomas 2021 年课程讲义），STPA 的本质是把发现前移到生命周期最早阶段。
2. **自下而上同样有效**。与愿先尝鲜的一线技术骨干（IC）合作，展示一次成功分析并亮出"从未有人发现过"的重大缺陷，震撼之后顺带一句"这是借助新技术发现的"。
3. **澄清四个常见误解**：(a) "要很多工程师投入数周数月"——那是航空航天与核电行业的标准；缩小分析范围、聚焦最关键 UCA，Google 用一到两名领域专家不到一周即可完成有限范围分析。(b) "发现不了前所未见的缺陷"——这是事后聪明偏见（hindsight bias），领域专家真正参与建模时常发现未知问题。(c) "只会得到冗长的待办清单"——不必穷尽一切，单一缓解措施常能消除整类脆弱性，设计阶段的轻量级修复也极其经济。(d) "需要多年专业培训"——寻求专家指导快速起步即可，Maps 分析正是数周边学边做的成功实践。
4. **选对系统与"快速试错"**。选择曾出现意外行为、有复杂交互、后果严重的系统，或仍处早期设计的系统；从小处着手、两三位参与者、一两天见分晓，远胜 10 名工程师数周颗粒无收。

**引入 CAST：影响力 / 可扩展性 / 效率**

1. **影响力**：让 CAST 产出切实可落地的工程项目以降低系统风险，并把 CAST 结果与事后总结并排对照，凸显其更深洞察。
2. **可扩展性**：已成功应用于涉及数百个软件组件与人员角色的事故，保留成功案例库作为最有力的佐证。
3. **效率**：耗时虽可能更长，但分析成果与建议即时共享，团队无需等最终报告出炉。城市名称事故的实测对比——事后总结 3 人 16 小时、6 项发现、8 条建议；CAST 5 人 81 小时、7 项发现、22 条建议——单位投入产出的洞察广度与深度远超传统方式。

## 实践要点

- [ ] 复盘时警惕"根因诱惑"：追问促成事故的系统性因素，而非停在第一个失败组件
- [ ] 给关键流程画分层控制结构（通常 5~10 个方框），让 SRE 与研发共建、消除理解偏差
- [ ] 用"未执行 / 过早 / 过晚 / 时长不当"四类模板给每个控制行为做 UCA 体检
- [ ] 事后总结之外补做 CAST：假设每个控制器在当时都合乎情理，先描述再解释
- [ ] 把 STPA 用在还停留在设计文档阶段的系统上——那是修复成本最低的时刻
- [ ] 推广时亮真实成果：一次成功分析 + 一个从无人发现过的重大缺陷
- [ ] 首次分析遵循"快速试错"：两三位参与者、一两天、有限范围
- [ ] 定期重新审视设计假设：数据与规模的环境变化会让原有控制手段悄然失效
