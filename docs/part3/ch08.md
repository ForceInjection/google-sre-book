## 核心概念

| 概念 | 术语（EN） | 说明 |
|---|---|---|
| 指标 | Metric | 对系统行为某一方面的量化度量，如 `http_responses_total_count` |
| 服务质量指标 | SLI | 服务性能表现的量化度量；建议表示为比值：好事件数 ÷ 总事件数 |
| 服务质量目标 | SLO | 为 SLI 设定的目标值，必须关联度量窗口（每小时/每天/30 天等） |
| 服务质量协议 | SLA | 未达标时后果处置的协议，通常表现为向消费方赔付的经济处罚 |
| 错误预算 | Error budget | 100% 可靠性与 SLO 目标值之差，即度量窗口内允许的最大不可靠度 |
| 消耗速率 | Burn rate | 消耗错误预算的快慢；等于 1 表示恰好能支撑到窗口期结束 |
| 核心用户旅程 | Critical User Journeys (CUJ) | 用户完成关键任务所经历的一系列步骤，须从用户视角、跨服务层级定义 |
| 隐式 SLO | Implicit SLO | 服务的历史表现水平——用户实际感知并依赖的"非正式契约" |
| 故障分钟数 | Bad minute | 客户端 SLO 建模法：以 1 分钟为间隔判定"故障"，SLO 表示允许的故障分钟数 |
| 会话化 | Sessionization | 用"某周期内遭遇某事件的会话百分比"定义 SLI，解决客户端分母未定义问题 |
| 海勒姆定律 | Hyrum's Law | API 用户足够多时，契约里承诺了什么并不重要，可观察到的行为都会被依赖 |
| 故障集中度 | Degree of concentration | 衡量故障在用户/标签群体中的分布集中程度，弥补单一 SLO 数字的盲区 |

## 关键论点

1. **SLO 同时是技术度量与组织机制**。它为业务方与技术方提供共同语言，围绕"客户应获得何种体验、如何确保落地"展开对话；目标值不应由工程团队拍板，而应由业务、产品、研发、运维组成的跨职能团队共同决策，因为 SLO 直接影响客户体验与商业结果。
2. **100% 从来不可达，也没必要**。成本梯度叠加无法彻底消除的边际损耗（如宇宙射线级事件）注定做不到 100%；错误预算则是自我强化回路的核心——超出目标时收紧风险、只做可靠性，预算富余时反而应承担更多风险（加快部署、小流量 A/B）。
3. **工程投入应随错误预算动态调整**（示意曲线，非标准建议）：基线约 10%~15% 精力投向可靠性；剩余预算降至约 25% 以下时投入在预算耗尽时达约 50%；严重翻红（超支）时约 90% 达峰。把服务 SLO 达标评估直接挂进研发迭代周期（如在 Sprint 复盘回顾），能让所有部门围绕"足够可靠"达成共识。
4. **SLO 贵精不贵多**：对大多数服务，通常只需不到 5 个高层级 SLO，既便于业务方掌控，又能约束架构设计选型并指导生产运维。目标可以从起步阶段的粗略值开始，随服务成熟持续调优。
5. **CUJ 把 SLO 延伸到用户体验领域**。由后端 SRE 单方主导的 SLO 只反映后端考量（系统 X 的存储延迟、推送流水线的端耗时）；"加入购物车可用性 99.9%"这类以用户为中心的 SLI 才能量出真实体验，并用客户端 SLI 与端到端合成监控（伪造完整请求而非只 GET 一下）兜底。
6. **单客户 SLO 是 B2B 场景的必然演进**。当单个客户贡献收入的两位数百分比时，全产品聚合 SLO 会掩盖其实际业务中断。它的回报是主动事故检测（在客户注意到之前先发出告警）、更窄的排查切入点和为高价值核心工作负载提供的额外保障；代价是精细化管理——客户元数据仓库、PII 匿名化、告警保真度与随客户数增长的扩展难题。
7. **隐式 SLO 才是用户记住的契约**。把 99% 拉到 99.999% 会惹恼为适应旧水平建好防御设施（缓存、重试、客服联动）的调用方——可靠性提升反而诱发更无禁忌的调用（杰文斯悖论 Jevons paradox）；把五个 9 放宽到三个 9 更会被视为转嫁降本恶果。Chubby 刻意制造受控故障中断、把可用性压在"刚好达到 SLO"，正是消除隐性依赖的极端实践。
8. **客户端 SLO 有四大挑战**：异步长调用链使插桩复杂（可用抽框模型显式标记开始/结束）；网络与老旧设备造成较高本底噪声（可用"故障分钟数"模型吸收，如把阈值设在噪声之上并给 30 天 43 分钟预算）；崩溃、卡死等事件缺少分母（会话化可解，但要保证类内事件严重程度相当）；复杂 SLI 让人看不懂系统到底在监控什么（须建立标准化定义与指导方针以赢回信任）。
9. **SLO 模型本身有局限**。它假设度量对象是可数的离散事件且能明确归功/归咎——AI 模型"协议层成功、应用层有害"的响应动摇了这一假设；响应端（SLO 违背时怎么办）被过度简化为布尔型"人是否介入"，把锯齿状响应模型制度化，无法体现中间过渡与预防价值；错误预算严重超支时如何处置始终棘手（1 月耗尽全年预算不可能全年冻结发布），按月刷新预算并让修复项目跨月持续推进是成本较低的实用机制。

## 落地方法论

1. **定目标**：跨职能讨论"为什么"，把 SLO 与业务目标绑定（如"购物车结账 4 个 9，其余 3 个 9"）。
2. **选 SLI**：从用户最常用/最重要核心操作的正常路径（happy path）入手，参照"请求/响应、批处理、存储"三类常见 SLI 菜单，先粗糙后迭代。
3. **定阈值**：区分可用性阈值（几个 9，起手 99.9%）与质量满意度阈值（延迟等，参考 WPOstats；无数据时以 100 ms≈瞬时、1 000 ms≈迟钝起步）。
4. **自动化告警**：直接从 SLO 推导多窗口、多消耗速率告警（1 小时烧掉预算 2% 触发快速告警，3 天窗口烧掉 10% 触发慢速告警，评估窗口 30 天）；低流量服务改用二项检验。
5. **治理与迭代**：统一工具收敛（Google 内部"SLO Repository"自助定义 SLI/SLO），给 SLO 打组织归属与生命周期标签（实验性/愿景性/承诺性/已废弃），并在复盘与人力规划中持续引用。

## 案例研究：以用户为中心的 SLO 捕获故障

Google 访问代理强制执行全球员工的内部请求信任策略，过去只有一个"以服务为中心"的 99.999% 可用性 SLO（基于对静态后端的合成探测）。监控与内部告警合起来捕获了绝大多数故障，但仍有几次故障 SLO 全绿、用户却已遇到问题——原因是若干使用场景流量极小，即便损坏也不足以触发告警。团队改为把"每种协议 × 目标类型"的组合各定义为一个 CUJ 并构建合成监控，形成全新的以用户为中心的 SLI。此后每一次访问代理重大故障都被基于 SLO 的告警精准捕获。

## 关键数字

- 30 天窗口内 99.9% 可用性 SLO ≈ 最多允许 43.2 分钟停机。
- 低流量服务的经典分界：每小时请求量不足约 100 次的服务难以用常规消耗速率告警。
- 二项检验示例：SLO 99%、要在 1 小时窗口检测 14.4 倍消耗速率（P=14.4%）、99% 置信度 z=2.575 时——N=1 000 需观察到 173 次失败（17.3%）、N=200 需 42 次、N=100 需 24 次才触发告警。
- 故障分钟数示例：本底噪声约 5% 时，把"故障分钟"定义为错误率超过 6%，30 天给 43 分钟预算；换算下来"99.99% 正常分钟数"对应按常规算法不到 95% 的请求成功率。
- 故障集中度示例：欧洲成年男性平均身高 178 cm、标准差 7 cm——68% 落在 171~185 cm、95% 落在 164~192 cm；标准差越小，分布越收敛，本身就是一种"集中度"度量。

## 实践要点

- [ ] SLO 目标值由业务、产品、研发、运维跨职能共同拍板，并向所有人解释"为什么不是 100%"
- [ ] 从核心操作的 happy path 选 SLI，先做粗糙版本（如负载均衡器入口返回码）再迭代到逐 RPC 综合
- [ ] 大多数服务控制在 5 个以内高层级 SLO；起步阶段可先承认粗略目标再持续调优
- [ ] 把 SLO 达标评估挂进 Sprint 复盘，按错误预算动态调配功能开发与可靠性工程的投入比例
- [ ] 服务依赖复杂时用"两头兼顾"策略：从最终用户 SLO 与核心组件 SLO 两端同时切入、小范围起步、逐步向中间汇合
- [ ] 缺遥测数据时先用 RED（请求率/错误率/持续时间）与 USE（使用率/饱和度/错误）框架找切入点，理解加深后果断替换
- [ ] 为高价值客户提供单客户 SLO：聚焦其关键工作负载、自定义阈值、建客户元数据仓库、监控全程匿名化，并与后果协调解耦内部错误预算策略
- [ ] 消除隐式 SLO 的办法是显式化：变更服务水平前"过度沟通"，并定期核对用户真实感知与 SLO 数字
- [ ] 客户端 SLO 用"故障分钟数"吸收本底噪声，用会话化解决分母缺失，用标准化 SLI 定义赢回信任
- [ ] SLO 工具全组织收敛统一（避免每个团队自建一套），并用标签管理组织归属与生命周期状态
