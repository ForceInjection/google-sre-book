    第20章 · SRE 如何赋能 AI#

    [!INFO] 出处 《SRE：Google 运维解密（第2版）》第Ⅵ部分 · 第20章 · 撰稿：Dan Dennison、Isaac Albarrán Muñoz、John Lunney 和 Rita Lu（合著：Garrett Holthaus）

    一句话概括：把 SRE 学科的整体方法论——SLO、准入认证、容量规划、能耗管理、安全合规——移植到概率化的 AI/ML 工作负载上，解决"迭代极快 + 资源极贵 + 输出不确定"这三重新约束。

    本章脑图#

    核心概念#

    概念 术语（EN） 说明
    持续训练 Continuous Training (CT) 把训练流水线自动化、周期化运行的生产范式，防止模型随时间推移退化
    ML 有效吞吐 ML goodput 扣除中断与系统开销后，所分配资源真正执行有效计算的时间比例；训练负载的核心 SLO 指标
    首 Token 延迟 Time to First Token (TTFT) 流式生成模型的关键延迟指标，直接决定用户交互体验
    张量处理单元 TPU (Tensor Processing Unit) Google 自研 AI 加速器，与 GPU、Trainium 等同属极稀缺算力资源
    预测偏差 prediction bias 模型预测输出分布与真实观测结果间的漂移，是捕捉模型退化的低成本实时信号
    硬件可替代性 Hardware Fungibility 在抽象层屏蔽加速器细节，使工作负载跨类型（TPU/GPU）与跨代际无缝运行
    占空比 duty cycle 加速器利用率的代理指标，常按一周第 95 百分位（7d95）度量
    具备 SLO 准入资格 SLO-eligible 硬件或平台须经严格准入认证、证明能稳定承载生产负载后，才有资格被 SLO 覆盖
    存证与证明 evidencing / attestation 以密码学手段向用户透明证明安全合规状态；证明失败等同服务中断（如 Private AI Compute）
    模型即裁判 model-as-a-judge 用高阶模型给 AI 输出与工作流打分评估，弥补传统统计监控对细微质量的盲区
    组调度 Gang Scheduling 紧密耦合的分布式训练作业必须同时调度全部任务，是 ML 集群的关键调度原语
    电力超配 Power Oversubscription 电力容量仅能支撑 100 台机器却实际调配 105 台，以换取消耗端利用率的整体提升

    关键论点#

    1. 可靠性的定义被改写。AI 输出是概率性的，"返回 200 但内容错误"同样是失败；SLI 必须延伸到 HTTP 状态码之外，度量降级响应、安全过滤触发与输出正确性。
    2. AI 的 SLO 拆成四支柱：可用性（含专用硬件与控制面）、吞吐量（ML goodput）、延迟（TTFT、任务调度、数据新鲜度）、质量（正确性、公平性与工具调用成功率），并须沿技术栈逐层传导、切实可扞卫。
    3. 模型评估分数本身就是 SLI。在自动化评估工具中为分数划定阈值即为 SLO，"捍卫 SLO"由排查修复事件变为常态职责。
    4. 垂直集成平台产生飞轮效应。统一硬件、函数库与编译器（如 XLA/Pathways），避免散定制方案无法规模化，基础设施改进惠及所有团队。
    5. 加速器贵到改变一切。N+1 冗余、发布缓冲等传统可靠性投入在 AI 场景财务上难以承受，必须用损耗框架逐项归因并工程化缓解。
    6. 准入认证贯穿产品生命周期。从 EVT 阶段起以统一测试策略（性能是否达标、输出是否正确、相对质量如何）持续认证硬件与模型，性能与质量双重回归是发布门禁。
    7. 能耗是一等资源约束。ML 机器功耗约为纯 CPU 机器的 3 倍，训练作业功率呈"方波"式秒级爬升；电力超配 + 低延迟反馈闭环 + 分级卸载，才能在断路器跳闸前压降功耗。
    8. 安全面被显著放大。控制逻辑与用户数据在同一通道混杂导致提示注入成为根本性弱点；缓解之道是把控制机制嵌入模型服务平台，规模化落地审计与强制约束。
    9. 平台化要把握时机。过早强制接入集中平台会扼杀探索产品市场契合度的速度，早期接受定制化方案、成熟后再收敛。

    加速器损耗分析框架#

    以 100% 利用率为理论基准，任何低于该基准的差额即视为损耗；归一化后区分"不可避免"与"可工程化缓解"两类。六大损耗：

    损耗类型 成因 推荐缓解方案
    最大利用率损耗 延迟 SLO 与物理极限：严格实时推理 50% 利用率即排队，异步批处理可安全至约 90%；自回归解码受内存带宽而非算力限制 用可替代流量对关键模型高频负载测试；红线金丝雀（redline canary）压出真实崩溃点；纳入 CI/CD 检测性能回退
    未实现需求损耗 功能发布推迟或爬坡低于预期，留下发布缓冲与过度供给的冗余容量 可抢占工作负载承接闲置（训练/评估/批处理）；容量池化共享；按爬坡节奏阶梯式扩容
    冗余（N+1）损耗 传统 N+1 容量调配在超大规模 AI 负载上代价高得难以承受 用更大的 N 稀释"+1"占比（代价是故障域变大）；把冗余要求限定在关键程度相当的工作负载或用户层
    解耦不均衡损耗 解耦模型服务中 prefill 与 decode 独立扩缩容，比例失衡导致瓶颈与容量搁浅 持续监控生产瓶颈，动态调整 prefill/decode 服务器比例，用代表性流量组合负载测试验证
    负载均衡损耗 请求处理开销极不均衡（Prompt 长度、解码步数），KV 缓存局部性与均匀分布路由冲突；轮询算法失效 换用最小负载（Least-Loaded）、峰值指数加权移动平均（Peak EWMA）等动态算法；按输入 Token 数做开销感知路由；全局流量整形
    碎片化损耗 每个 LLM 都有最小服务占用空间（示例中每集群约 100 颗芯片），多产品独立部署同一模型会白白浪费闲置余量 模型聚合、限制变体数量；优先用系统提示词（Prompt 工程）而非微调定制；跨产品多租户共享部署

    SRE 如何支撑 AI 工作负载#

    • 数据质量分层防线：依赖追踪（用数据血缘构建依赖树，跌破阈值自动告警并中止下游 ML 流程）→ 统计监控（持续校验输入/输出分布形态，捕捉预测偏差）→ AI 辅助评估（动态错误阈值、model-as-a-judge，周期性或小比例抽样运行）。
    • 质量降级的可观测性：在服务层插桩记录系统何时主动降级（容量紧缺时路由到更小模型）或触发安全过滤器；在应用层跟踪显式反馈（点击）与隐式行为信号（重写 Prompt、放弃会话）；再对这部分"技术层成功"的响应抽样进入异步评估，把主观降级转化为可度量的 SLI。
    • 发布 AI 功能五步法：分阶段发布与实验（A/B 对比模型版本）→ 全方位监控（输出质量、数据/预测漂移、降级频率）→ 容量管理（负载测试与 GPU/TPU 成本效益）→ 快速回滚（模型版本控制）→ 持续反馈循环（评估流水线 + 用户数据回流爬山法迭代）。

    案例细节：推理负载的调度与作业优化#

    • 调度原语：拓扑感知调度（感知高速芯片间互连 ICI 连接的 TPU 切片约束）、组调度（Gang Scheduling）、有效吞吐感知调度（按执行进度设定优先级）、加速器拓扑碎片整理（保留大片连续加速器供大模型使用）。
    • 作业优化：同一在线服务单元内的多模型装箱混部；按 HBM 与算力占用做资源隔离、支持模型动态加载卸载；关键生产作业与低优先级训练/科研作业混跑，用抢占（preemption）回收资源，并配合频繁高效的检查点（checkpointing）把作业损失降到最低。
    • 自动容量规划：改造推理引擎上报每次查询成本；区分自然增长需求与非自然增长需求（新功能、互动引导、模型变更、硬件换代）；小流量实验外推全量部署——自动化容量规划负责中期基准容量，自动扩容负责短期突发峰值。

    实践要点#

    • 为 AI 系统定制四支柱 SLO：可用性（含硬件与控制面）、ML goodput、TTFT、输出质量
    • 用数据血缘建依赖树，上游数据质量跌破阈值即自动中止下游训练/推理
    • 在服务层插桩记录主动降级与安全过滤触发，把质量降级变成可度量 SLI
    • 发布 AI 功能走五步：分阶段实验、全方位监控、容量管理、快速回滚、持续反馈
    • 用红线金丝雀压测关键模型摸清真实崩溃点，并把检查集成进 CI/CD
    • 用六大损耗框架归因利用率缺口，优先投入可工程化缓解的部分
    • 调度器补齐四个 ML 原语：拓扑感知、组调度、goodput 感知、碎片整理
    • 抢占机制配高频检查点，用低优先级作业填充在线服务回落出的闲置容量
    • 电力异常响应次序：先限流；持续超 5 秒再视资源余量触发任务终止或机器关机
    • 为 AI 特有组件增强可观测性：记录提示词与响应（脱敏）、工具调用、智能体推理轨迹
